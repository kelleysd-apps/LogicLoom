LogicLoom · Architecture Artifact

A thin governed core, packages you choose, and a layer nothing may overwrite.

LogicLoom builds only the hook-enforced governance floor, the constitution, and the machinery that updates them. Every capability is a package — adopted where a tool already exists, built only where nothing existing can read what we have. Everything a person adds is an enhancement the harness can never step on. And because the floor is repo-committed shell hooks, it travels to every surface Claude Code runs on.

v6.3.1 · constitution v3.2.0 2026-07-09 vision locked · 9 decisions · 14 findings · 5 corrections

What this artifact is. The who, what, why, and where — the vision, the verified problems standing in its way, the constraints that are settled, what we got wrong along the way, and the full record of what was written.

What it deliberately is not. A plan. No sequencing, no phases, no work order. How and when are decided at planning time, by whoever plans. Artifacts are what you plan from, never what confines the planner.

Why

Three requirements that turned out to be one mechanism

The harness must stay light, its packages must update independently, and nothing a person writes may be lost to an update — on any surface they work from.

These looked like three problems. They are one: Claude Code already merges configuration in layers, and every surface reads the same layers. A person's settings, commands, and connectors sit in the user layer. The harness sits in the project layer. Packages sit in the plugin layer. They coexist by precedence rather than by overwriting each other.

So customization survives updates not because we built a merge engine, but because the updater structurally cannot see the user's files — they are out-of-repo or ignored — or is explicitly forbidden from touching them. The entire model is filters, conventions, and one configuration file. There is no engine to write.

What

The orchestrator

Rungs are roles, not model tiers. Delegation buys context isolation, effort asymmetry, tool scoping, and parallelism — only one of which is model identity.

A frontier orchestrator plans, reasons, and delegates; a deep reasoner takes architecture and hard debugging; a fast worker takes boilerplate. When the frontier model is unavailable, the top two rungs merge in model but stay distinct in role — you reason inline when context is cheap, and delegate when you need a clean window, higher effort, or several reasoners at once.

Non-Claude models cannot orchestrate — by construction of the host, not by our policy. A subagent accepts Claude aliases or model IDs only; Bedrock, Foundry, and Vertex all still route to Claude. There is no toggle that changes this. Other providers enter at exactly one place: the advisory layer, where a different model lineage reviews a bounded artifact through an API, or explores the repo through a read-only sandboxed CLI, and returns findings a governed Claude agent triages. It never writes source, never runs git, and never decides control flow.

The reason a different provider matters is decorrelation: a same-lineage self-review shares your blind spots. Where no second lineage is reachable, the honest thing is to say so rather than call a self-review a cross-check.

Reaching that second lineage is where the design is thinnest. Only two providers are wired, by name. One generic slot — a configurable endpoint for any OpenAI-compatible API — would reach Grok, every hosted open-source gateway, and a model running on your own machine. It does not exist yet, and it is the cheapest reach the harness could buy.

What leaves the machine is a governance question, not a convenience. The advisory commands are the only path by which this repository's contents reach a third party. Nothing outside the repository, and nothing git has been told to ignore, may travel with them — a rule that also keeps the file holding your API keys from being mailed to the provider those keys belong to. It is sound only once the ignore rules actually work. And an outside command-line reviewer may be trusted with the repository only if it can run in a sandbox that cannot write.

What

The graph stack

Every project gets a built-in knowledge graph and code graph, in-repo, reproducible, on every surface. Nothing is adopted into the default path.

A deterministic harvester emits a git-tracked graph from what the harness already writes — manifests, frontmatter, hook wiring, and the wikilinks and supersession edges its memory has been recording all along. A committed Mermaid file gives a person a picture wherever they already are. No database, no daemon, no port, no model call.

"Visual tools for the agent" is mostly a category error. An agent queries the graph; a rendered picture is a lossy re-encoding for retinas it doesn't have. The single exception is a small scoped diagram used as context compression — text the model both reads and writes.

And the reason adopting an existing tool fails here is worth stating once: every code-graph tool reads language syntax trees. This harness's structure lives in JSON manifests and markdown frontmatter, and this repository contains almost no code to parse. There is nothing to adopt. Adopt-existing remains right for product code — which is exactly where the optional tools are queued.

How it teaches

The harness reports; it never recites

A capability nobody knows how to turn on is a capability nobody has. But guidance that repeats rules the hooks already enforce is ceremony — and that ceremony was deliberately removed.

The line between them is one sentence: inject facts, not rules. Restating the constitution every turn assumes the model forgets it. That assumption is false, which is why the recitation was cut. Telling the model that no second-provider key is configured tells it something it cannot know by reasoning — no amount of capability reveals the contents of an environment.

So guidance arrives in three places and nowhere else. A command that cannot do its job says so at the moment it is called, never degrading in silence and never calling a self-review a cross-check. A prompt that would have benefited from a capability gets a nudge when it is relevant, carrying the single line that enables it. And one doctor command, run on demand, reports which hooks actually fired, which surface you are on, which model you are running, and what is out of reach.

Every value it names lives in a file an update can never touch. Detection belongs to the harness; configuration belongs to you. There is no installer, no wizard, and nothing writes to your files on your behalf.

Where

Every surface, honestly

The floor is nothing but repo-committed shell hooks. It fires wherever the repository is cloned and a shell runs — which, correcting a long-held assumption, includes the cloud.

That is why the orchestration agents live in the project layer — it's what makes them portable. And a person's connectors never collide with the harness's, because same-name conflicts resolve by precedence rather than clobbering.

What must be addressed

Verified problems

Each was read from the repository or reported by a downstream fork, then confirmed here. Nothing below is inferred.

Critical

The published template cannot update itself

verified in repo

The update baseline shipped on the public branch points at a commit that no longer exists in that branch's history — the sanitized release rewrote it away. A fresh clone cannot compute the diff the updater depends on. This breaks the single feature the whole customization-preserving model rests on. It is invisible from the maintainer's branch.

main         .sdd-sync-ref=c6092b086256  → ancestor of main ✅
origin/main  .sdd-sync-ref=6c4c42067161  → NOT ancestor of origin/main ❌
High

Cloners commit their private overrides

verified in repo

The repository's ignore rules — .local/ and *.local — match neither settings.local.json nor CLAUDE.local.md, the designated homes for the customizations updates must never touch. They appear ignored only because the maintainer's machine-wide git config hides them.

git check-ignore -v .claude/settings.local.json
~/.config/git/ignore:14   ← the maintainer's machine, not the repo
Pattern

Nothing exercises what a customer actually clones

inferred from the two above

The two failures above are the same failure. Both look correct from the development branch and break on the published artifact. No test ever clones the template fresh and tries to use it. Until something does, this class of defect keeps shipping.

High

The frontier model runs out of credit and the session stops

verified · vendor docs

Claude Code's fallback chain fires only on overload or unavailability. The docs exclude the case that actually happens: "authentication, billing, rate-limit, request-size, and transport errors never trigger a switch." So an exhausted frontier model errors; recovery is a manual model switch.

The harness's own configuration names a fallback that nothing reads and that wouldn't fire anyway — a fiction twice over. A real fallback is one settings key away, and covers overload only.

High Decided

Workers are blocked from reading the repository

verified · downstream report

A subagent running git status, git log, or git diff is hard-denied with no path to approval. The guard tests whether a command is git, not whether it changes anything. The correct predicate already exists nine lines below.

governance-verdicts.sh:60  subagent → loom_git_is_invoke    (any git at all)
governance-verdicts.sh:69  main     → loom_git_is_mutation  (the right test)
Medium

Renamed forks get governance that guards nothing

verified · downstream report

The protection logic names its framework directories literally. A fork that renames them — or drops the harness into a monorepo subfolder — guards paths that do not exist, while the real constitution and hooks sit unprotected. Every check passes. Nothing is protected.

git-safety-gate.sh:66   cd "$SCRIPT_DIR/../../../.."   ← fixed depth
repo-wide               17 files resolve from git root · 42 walk up by hand
Medium

A customized constitution can lose its customizations

verified · downstream report

The constitution is one file holding both the core principles and whatever a project adds. The compliance checker validates its structure and never its content, so paragraphs a team wrote can vanish in a merge — and a team editing in place can quietly erode the core philosophy the same way. Both bodies of text are exposed to each other.

Medium

Packages cannot be updated individually

verified in repo

No marketplace file exists anywhere in the repository. Without one there is no per-package install, version, or update — so "each package updates on its own" is a claim the harness cannot honor.

Medium

The updater's boundary is a coincidence, not a rule

verified in repo

Nothing declares which paths the harness owns. A person's files are safe today only because upstream happens not to ship files with the same names. The guarantee that updates never touch user work is currently probabilistic.

Medium Unresolved

A referenced folder may be able to ship agents and skills

contested — needs a test

Adding an outside directory grants file access. Whether it also loads that folder's agents, skills, and plugin declarations depends on which mechanism you use, and two readings of the documentation disagree. If the permissive reading holds, a folder added for reference can contribute instructions to your session.

The safe posture until proven: use the settings key, never the command-line flag.

Medium

The memory writes edges nothing ever reads

verified in repo

The memory is already a wiki: every note carries frontmatter, links its neighbours, and records what it supersedes. The search reads none of it — it matches keywords and stops. And the graph harvester, which does parse links, emits zero supersession edges because it never learned that vocabulary.

So the project's own history of what corrected what is written down, in order, by hand — and is invisible to everything that reads it.

Medium

A second opinion is reachable only from two vendors

verified in repo

The adversarial reviewer names its providers literally, and there is no configurable endpoint anywhere in the configuration. Grok, every hosted open-source gateway, and any model on your own machine speak the same API shape — and none of them can be reached.

For a design whose whole premise is that a different lineage catches what yours cannot, being able to reach exactly two lineages is a thin margin.

Low Decided

A provider policy is written as constitutional law

downstream report

"Orchestration runs Anthropic models only" is encoded as a principle. The mechanism it rides on is portable and correct; the policy is not. A team running other providers cannot adopt the principle without importing a claim that is false for them.

Low

The floor does nothing until it is wired in

downstream report

Copying the guard scripts enforces nothing until they are registered. The failure mode is silence. There is no self-test that fires a guard and confirms it answered.

Forensics

What we believed, and what turned out to be true

Five load-bearing claims were wrong. Recording them matters more than quietly fixing them — each one shaped a decision, and one of them is still unsettled.

Cloud sessions don't load a project's hooks, so governance is silently absent there.

False. Repo-committed hooks are part of the clone and fire in cloud sessions. The surface where governance really is absent-while-looking-present is Windows without Git Bash, where hook commands fall through to a shell that cannot run them.

Understand-Anything's star count is implausible; treat the project as unverified.

Refuted. The repository is real, MIT-licensed, pushed daily, and has 72,337 stars. The version we cited was two minors stale. It is a better project than we represented — and still cannot be a bundled default.

Adopt Understand-Anything; the graph we built is an extraction target.

Reversed. Its graph is model-generated and therefore not reproducible; its dashboard requires a server on a port; a cloner cannot inherit its build; and its auto-update hooks instruct the agent to act without asking — in a harness whose first principle is that git never runs autonomously. Adopt-existing presumes an existing tool can see your data. None can read manifests and frontmatter.

If the frontier model is spent, the orchestrator quietly falls back to the next tier.

False. Billing and rate-limit errors never trigger a fallback. The session stops. The configured fallback covers overload only — and nothing in the harness reads the file that names it.

Granting access to an outside folder is a read-only text window.

Unresolved, and it is the security boundary. That folder is writable by default, and on one reading of the documentation it can also contribute agents, skills, and plugin-marketplace declarations. Two verification passes disagreed. This needs a test before anyone relies on the absence of risk.

Settled

Decisions

Constraints for anyone planning this work. Not up for rediscovery.

01

The core philosophy is never overwritten — and every principle may still be overridden

LogicLoom's core principles stay canonical. An update never loses them; an amendment never rewrites them. Amendments overlay the core rather than editing it. A project may override any principle it likes — including the three called immutable — and doing so warns clearly and is recorded. It is never silent.

Two meanings of "immutable" were tangled together. The text deserves protection; the behavior is the owner's to choose. Preserving the core costs a project nothing, and departing from it should cost a warning — not a fork.

02

Amendments are tracked, shared, and never overwritten

They live in their own committed file, travel with the repository, and sit on the updater's denylist. The constitution a project actually runs under is the core plus its amendments, with every override announced where it can be seen.

A team's amendments belong to the team, not to one machine. And an override nobody notices is indistinguishable from a principle nobody follows.

03

Workers may read the repository; only mutations are gated

Subagent git switches from deny-everything to deny-mutations. Read-only inspection is allowed.

Gating what changes state — rather than what merely mentions git — is the more precise reading of the git-approval principle, not a weakening of it.

04

Provider policy moves out of the constitution and into configuration

The model-selection mechanism stays constitutional. Which providers may orchestrate becomes a setting.

Mechanism is portable; policy is local. A team should not have to amend its constitution to describe its own runtime honestly. Note that on this host the answer isn't a policy at all — a subagent cannot be a non-Claude model.

05

The graph stays ours; nothing is adopted into the default path

The deterministic harvester becomes the bundled-default graph package. No model call, no database, no daemon, no port. Richer tools are optional, user-installed, and depended upon by nothing.

A built-in, in-repo, reproducible graph that works on every surface is a specification only a git-tracked text artifact passes.

06

Vaults leave the core entirely

Obsidian and any external knowledge store are tools a person may connect, exactly like any other external tool. The harness ships nothing for them and depends on nothing from them.

The repository is already a folder of linked markdown. There was never a vault to build — only one to open.

07

Cloud enforcement gets proven before it is promised

A live guard must fire in a real cloud session before the harness advertises uniform governance across surfaces.

The documentation says it works. Documentation is not evidence, and this claim is load-bearing.

08

Artifacts carry no plan

Vision, research, forensics, and documentation live in artifacts. Sequencing lives in a planning phase, or is left to the agent doing the work.

A plan baked into an artifact pre-commits decisions that belong to planning time, when more is known — and confines the agent doing the planning.

09

The harness tells you what it cannot do

Facts get injected; rules do not. A capability that is unavailable announces itself when called, is nudged when relevant, and can be interrogated on demand. Nothing is recited each turn, and nothing writes to your configuration for you.

Restating rules assumes the model forgets them. Reporting the environment tells it something it genuinely cannot see — an assumption that stays true no matter how capable the model becomes.

Constraints

What must not be built

This harness has already cut a bespoke marketplace, a telemetry stack, and a workflow engine it did not need. The pattern repeats when native mechanisms go unexamined.

  • No merge engine, overlay system, package manager, or resolver. Every requirement here maps to something the platform already does.
  • No model call in the extraction path. A graph you cannot regenerate byte-for-byte is not an artifact; it's an expense.
  • No daemon, watcher, port, or lockfile. A template that must run a process is not a template.
  • No new clone-time binary dependency. The default must degrade to the tools already present.
  • The floor never becomes a package. Anything a person can disable is not a floor.
  • Nothing ignored, and nothing outside the repository, is sent to another vendor. The advisory commands are the only way out; that door stays narrow.
  • No outside reviewer runs unsandboxed. An external tool may read this repository only if it can be prevented from writing to it.
  • No ceremony. Guidance states facts the model cannot see; it never recites rules the hooks already enforce.
  • No plan inside an artifact. Sequencing belongs to whoever plans, when they plan.

Unproven

What still needs evidence

Three claims are load-bearing and rest on documentation alone. Each is cheap to test, and none should be advertised until it is.

Does the governance floor actually fire in a cloud session?

The carry-over table says repo hooks are part of the clone. Run one throwaway denying hook in a real cloud session and watch it deny.

Does a referenced outside folder load its agents and skills?

Point a session at a scratch folder containing a skill, and see whether the skill appears. This single test decides whether connecting an outside knowledge store needs mediation.

Does the configured fallback catch a frontier-model overload?

Worth knowing before it ships as the core default — especially since it provably will not catch the exhaustion case people actually hit.

And two things are undecided rather than unproven

Where the project's memory truly lives. The wiki with the richest link structure — the one written at the end of each sprint — sits outside the repository, on one machine. It never reaches the cloud, a teammate, or a continuous-integration run. The in-repo corpus is nearly as densely linked and travels everywhere. Declaring the in-repo corpus canonical is the safe answer; it trades away graphing the most-linked notes you have. Nothing built-in may depend on a path in someone's home directory.

Which package owns the edge parser. The graph reads the memory's links; the memory's search needs to walk them. Both are bundled defaults, so only the file ownership is in question.
