# =============================================================================
# LogicLoom — adopt-package PAYLOAD MANIFEST  (PROPOSAL, not a settled decision)
# -----------------------------------------------------------------------------
# WHAT THIS IS
#   The adopt package installs a SUBSET of the harness into someone else's
#   existing repository. Which subset is what "LogicLoom adopted" means, so it is
#   a product decision, not a research finding. This file is the recommendation
#   from .docs/design/adopt-package-research.md § 6 PRE-1, re-derived row by row
#   against the repo, with the evidence inline. It is REVIEWABLE: the maintainer
#   overrules it by editing this one file. Nothing reads it yet — the installer
#   is not written. tests/contract/test_adopt_payload_manifest.sh is the only
#   current consumer, and it holds the boundary to the invariants below.
#
#   THIS FILE IS MAINTAINER-ONLY. `packaging` is a template-strip-manifest entry,
#   so nothing under packaging/ ever reaches a customer or an adopter.
#
# WHAT THE PAYLOAD IS BUILT FROM
#   A tag on the PUBLIC `main` (research § 3, PRE-4) — i.e. an ALREADY-SANITIZED
#   tree. Everything template-strip-manifest.txt removes is therefore already
#   gone before this manifest is applied: .brain/ is README-only, artifacts/ and
#   packaging/ do not exist, VISION.md / todos.md / backlog.md are stubs, the
#   release scripts are stripped. Entries below that name an already-stripped
#   path are DEFENSIVE — they cost nothing and they survive a change of source.
#
# GRAMMAR — DELIBERATELY DIVERGENT FROM template-strip-manifest.txt, AND WHY
#   Same line-oriented shape, same `#` comments, same "globs match against
#   `git ls-files` output" model. One deliberate difference: EVERY line carries
#   an explicit verb. There is no bare-path form.
#
#   The strip manifest's bare path means REMOVE. This is an INCLUDE list, so a
#   bare path here would mean the exact opposite in a file that otherwise looks
#   identical, and the two get copy-pasted between. A silent inversion of the
#   default is how the wrong thing ships. One verb per line costs six characters
#   and makes the inversion impossible. That is the whole divergence — a second
#   grammar was not invented, the first one was made explicit.
#
#     include: <path-or-glob>        Copied verbatim into the payload. A
#                                    directory entry is recursive.
#     exclude: <path-or-glob>        NOT shipped. Recorded rather than omitted so
#                                    every "no" has a reason a reviewer can read.
#     rename:  <src> :: <dst>        Shipped, installed at a different path.
#     merge:   <path> :: <strategy>  NEVER overwritten in the adopter's repo.
#                                    Additive, marked, idempotent.
#     defer:   <path> :: <question>  UNDECIDED. Neither shipped nor dismissed.
#                                    The installer must refuse to run while any
#                                    `defer:` line stands — mirrors the strip
#                                    manifest's `warn:` verb, which exists so a
#                                    deferred decision cannot ship silently.
#     author:  <src> :: <dst>        AUTHORED BY THIS PACKAGE, not carried in the
#                                    payload. `src` resolves against the PACKAGE
#                                    root (beside merge/), never the payload root.
#                                    That different resolution base is the whole
#                                    reason it is a sixth verb rather than a
#                                    `rename:` — a `rename:` source is looked for
#                                    under the payload root, where in a packed
#                                    release these files do not live, so the row
#                                    would resolve in a dev checkout and vanish
#                                    once published.
#
#   An `exclude:` beats an `include:` that would otherwise cover the same path.
#   That is the only precedence rule; there is no wildcard and no "ship
#   everything" line.
#
# NODE / npm FLOOR FOR THE PUBLISH WORKFLOW  (PRE-12) — READ BEFORE WRITING
# .github/workflows/publish-adopt.yml
#   npm trusted publishing (OIDC from GitHub Actions) requires
#   Node >= 22.14.0 and npm CLI >= 11.5.1, and runs on GitHub-HOSTED runners only.
#
#   *** VERIFIED 2026-08-27 *** against the primary source,
#   https://docs.npmjs.com/trusted-publishers, which states verbatim:
#     "Trusted publishing requires npm CLI version 11.5.1 or later and Node
#      version 22.14.0 or higher."
#   and, on runners:
#     "Self-hosted runners are not currently supported but are planned for
#      future releases."
#
#   RUNNER CONSTRAINT — every workflow in this repo is `runs-on: ubuntu-latest`,
#   a GitHub-hosted runner, so we satisfy it today. Recorded because a future
#   maintainer moving CI to self-hosted runners would break trusted publishing
#   with no local signal.
#
#   These figures WILL move. Re-check with:
#
#       curl -s https://docs.npmjs.com/trusted-publishers | grep -iE 'node|npm .?[0-9]+\.|self-hosted'
#
#   What IS verified in-repo, today: .github/workflows/plugin-tests.yml and
#   .github/workflows/promote-to-main.yml both pin `node-version: '20'`, and root
#   package.json declares `engines.node >= 18.0.0`. NEITHER WAS BUMPED, on
#   purpose — neither workflow publishes, so raising their floor for an unrelated
#   reason is churn. The consequence is the trap this note exists to close:
#   publish-adopt.yml must carry its OWN `actions/setup-node` step with a
#   satisfying version. It will NOT inherit one, and copying a step from either
#   existing workflow silently gives it Node 20.
#
#   Also recorded at .docs/design/adopt-package-research.md § 6 PRE-12.
#   tests/contract/test_adopt_payload_manifest.sh asserts this block still names
#   the versions, still carries a VERIFIED date and its source URL, and still
#   carries a re-check command — so it can be neither quietly promoted to fact
#   nor left to quietly rot once npm moves the floor.
# =============================================================================

# --- THE HARNESS'S OPERATING INSTRUCTIONS (was `defer: CLAUDE.md`; PRE-7) ----
# RESOLVED 2026-08-27. The deferred row asked how CLAUDE.md installs. The answer
# has two halves and they are answered in different places.
#
# HALF 1 — WHAT SHIPS. Not our CLAUDE.md, and not a split of it. Only ~23% of
# that file is an obligation an adopter must have loaded; the rest is reference
# (which already ships under .docs/) or FACTS ABOUT THIS REPO that are actively
# WRONG in someone else's — our version stamp, our parsed plugin table, our
# branch topology, our `.brain/` history, `/update-framework` and `.sdd-sync-ref`
# (clone-path machinery an npm adopter never touches, exactly as PRE-13 says of
# /initialize-project). Copy-then-subtract leaves those in until someone notices.
# So the rules below were AUTHORED for an adopter's repo, in the second person,
# stating only obligations that hold in any repo with the harness installed.
# Analysis and the line-by-line classification: .docs/design/claude-md-split.md.
#
# ~226 lines across three files against an 860-line source. That budget is the
# point, not a nicety: rules files without `paths:` frontmatter load at launch at
# the same priority as .claude/CLAUDE.md, so every line is paid for on every
# prompt of every session, and the vendor's own guidance is under 200 lines per
# file because "longer files consume more context and reduce adherence". Shipping
# 860 would push a typical adopter's combined instruction set to ~6.8x that
# target and crowd their own product rules to roughly a third of what is loaded.
#
# NOT SHIPPED, and it is not an oversight: `.claude/rules/` is invisible to
# build-graph-bridge.sh (zero references), so anything installed there is outside
# the graph index. Recorded, not fixed — the fix belongs to that script.
exclude: CLAUDE.md
author: payload/rules/logicloom-governance.md :: .claude/rules/logicloom-governance.md
author: payload/rules/logicloom-workflow.md :: .claude/rules/logicloom-workflow.md
author: payload/rules/logicloom-file-rules.md :: .claude/rules/logicloom-file-rules.md
#
# HALF 2 — HOW THEY RELATE TO THE ADOPTER'S OWN CLAUDE.md. That is not a
# manifest decision, because it is not ours to make: it is chosen at init time,
# per project, and executed DETERMINISTICALLY. Three modes, in lib/claude-md.js,
# selected by `--claude-md=<mode>` or `LOOM_ADOPT_CLAUDE_MD=<mode>` — a flag or
# an environment variable, never a prompt, so a scripted or CI install works:
#
#   rules   (DEFAULT) install the three files above; their CLAUDE.md is never
#           opened, read, or written.
#   import  the same files PLUS one marked block appended to their CLAUDE.md
#           carrying an `@` import of each. The hedge for the one thing the
#           analysis could NOT verify end-to-end: project-scope `.claude/rules/`
#           loading (§ 0, § 8). If it does not load, `rules` installs 226 lines
#           nothing reads — a silent, total failure. `import` costs one block.
#   none    install nothing loadable. The harness tree still installs and the
#           reference material still reaches them under .docs/.
#
# The mode resolves as a pure function of (flag/env, does a CLAUDE.md exist).
# With no CLAUDE.md the question is NOT ASKED and `import` collapses to `rules`,
# because this tool never creates a CLAUDE.md. The resolved mode is recorded in
# .logicloom-adopt-receipt.json, so a re-run and an uninstall both know what
# happened. `--only=all` includes the rules target but can never reach their
# CLAUDE.md: `import` has to be typed.

# --- EXCLUDED: THE NON-NEGOTIABLE ROW ----------------------------------------
# .github/ — ALL FIVE WORKFLOWS, and the directory itself.
#
# The reason is sharper than the research states. The exclusion of the maintainer
# workflows otherwise happens ONLY inside /initialize-project (init-project.sh +
# the project-initialization skill + initialize-project.md, held in lockstep by
# tests/contract/test_shipped_gates_vs_strip.sh), and NO ADOPT-SIDE PATH REMOVES
# THEM. The payload is the only place the exclusion can happen.
#
# UPDATED 2026-08-27 (PRE-13 resolved). The research's line was "an adopter never
# runs /initialize-project, so nothing downstream will ever remove these". The
# first half is FALSE and was never enforceable: this payload ships plugins/ and
# .claude/commands/, so /initialize-project IS in an adopter's palette. What is
# true is the CONSEQUENCE, and it now runs the other way — /initialize-project
# detects the adopt receipt and SKIPS its CI-removal step outright, because with
# .github/ excluded here every workflow in an adopted repo is the adopter's own
# and `rm -f` against it would delete their work. So this row is not merely still
# load-bearing; the skip is only safe BECAUSE of it.
#
# What breaks if it does not:
#   branch-topology-guard.yml — fails EVERY pull request into `main` whose head
#     branch is not release/vX.Y.Z. An adopter inheriting it has every PR fail on
#     day one. This alone settles the row.
#   plugin-tests.yml — bare `on: push` / `on: pull_request`, and it runs the
#     harness bash contract suite. With tests/ excluded it fails immediately.
#   promote-to-main.yml, release-tag.yml, leak-guard.yml — our release loop.
#     Meaningless in a foreign repo, and they name our topology.
#
# The entry is the DIRECTORY, not a five-file list, for the same reason the strip
# manifest's `packaging` entry is wholesale: a sixth workflow added later is then
# already covered, with no release-day edit to remember.
exclude: .github
