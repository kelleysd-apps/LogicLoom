## Governing constraint

Every disposition below was decided against the maintainer's stated goal, verbatim:

> "give LogicLoom users a clear usable harness from the install but not overbearing on their own preferences they may want to implement."

That cuts both ways. It **rejects** anything that reaches outside the repo, hardcodes the maintainer's own topology into a customer's tree, or ships an opinion a fork cannot override (§4, §3.1's caveat, §1.4's risk). It also **rejects** shipping a check that lies about what it verified, because a broken default is not a neutral one (§1.1, §1.2). "Not overbearing" means configurable and honest — not absent.

### `66e4dbf` — governance tokenizer fix

Command-position anchoring for git **invocation** detection, subcommand anchoring for **mutation** detection, and the same fix applied in `protect-governance-files.sh`.

- **False denials removed:** `grep --exclude-dir=.git`, `sed -i.bak`, `ls foo/.git`, and `echo "check git status later"` were all **DENIED** for subagents purely on the substring `git`. `git stash list`, `git tag -l`, `git log --grep=push`, and `git branch -a` all prompted for approval as if they mutated.
- **Two false ALLOWs closed in passing** (both tightenings, not relaxations): bare `git branch <new>` was ungated, and a **line-leading** `rm`/`mv` against a protected path bypassed governance-file protection entirely, because the old regex required surrounding whitespace.
- **Result:** verdict table 54/62 → **62/62**; protected-path table 44/56 → **56/56**.

### `38b0144` — closed the gating inversion

`gh pr create`, `gh pr merge`, and `gh workflow run` returned **allow** for both the main agent *and* subagents — no hook or policy matched `gh` at all.

- **Now gated:** `pr` create/merge/close/reopen/review/edit; `workflow` run/enable/disable; `run` rerun/cancel; `release` create/delete/edit; `repo` delete/archive/edit; `issue` create/close/edit/delete/pin; `alias set`; `secret`/`variable set`; `ssh-key add`; `auth login/refresh`; and `git worktree add|remove|prune|move|repair|lock|unlock`.
- **Three laundering vectors closed:** `gh api -X PUT repos/o/r/pulls/N/merge` (merges without the word "merge"), `gh api -f/-F/--field` with no method flag (gh defaults to POST), and `gh alias set` (disguises later invocations).
- Read-only `gh` stays silent. **Subagents are denied `gh` wholesale, including reads** — deliberately categorical: a read/write split is one classification bug away from a silent merge.
- `git push --force` / `--force-with-lease` moved from `dangerous_commands` (hard block, no approval path) to `git_operations` (`require_approval`), satisfying "the hook should not stop the ask." All other `dangerous_commands` entries verified unchanged.
- **Result:** suite 586 → **597 assertions, 0 failures**.

**Test-integrity note:** `test_policy_matching.sh` asserted the old force-push hard block. It was **flagged and updated with an explanatory comment, plus a new group proving force-push is still gated** (now via approval rather than block) — the assertion was not silently weakened.

## 1. Verified defects (BUGS, not enhancements)

These are not proposals to improve the harness; they are things the harness currently gets wrong.

### 1.1 `constitutional-check.sh` overstates its own result

- **What:** `.logic-loom/scripts/bash/constitutional-check.sh` has exactly **one** `record_fail` call site (line 194, Principle VI) against **17** `record_warn` calls. Principle X is labelled `(CRITICAL)` at line 284, but its only outcome is `record_warn` at line 310. Line 531 prints `"All critical principles (VI, X) are met."` inside `if [ $FAIL_COUNT -eq 0 ]` — a condition Principle X can never influence.
- **Why:** The script asserts it verified X and structurally cannot. A compliance check that reports a stronger result than it computed is worse than one that reports nothing.
- **Disposition:** ADOPT. Either make X able to fail, or delete "X" from the success string. Recommend the second as the minimum honest fix, with the first as the follow-up — making X hard-fail changes exit codes for every existing consumer and should be its own decision.
- **Cost:** Minimum fix, one line. Full fix (X can fail) small, but touches exit-code contract. **Risk flags:** Not a protected file. Making X fail could break CI for downstream clones — gate behind a flag or ship as a minor-version behavior change.
- **Note:** Independently disclosed by Cosmos in their handoff §8. Inherited from the shared ancestor; present in both trees.

### 1.2 Stale `.claude/agents/` warning contradicts a ratified decision

- **What:** The same script warns (line 445) that `.claude/agents/` is legacy and agents belong in `plugins/*/agents/`.
- **Why:** Keeping `deep-reasoner` and `fast-worker` as **project** agents there was a deliberate v6.3.1 decision — plugin agents lose `hooks`, `mcpServers`, and `permissionMode`. A warning that fires on a correct configuration trains maintainers to ignore the check wholesale, which erodes §1.1's fix too.
- **Disposition:** ADOPT. Narrow the warning to unexpected entries, or drop it. **Cost:** Trivial. **Risk flags:** None. Not protected.

### 1.3 Promote PRs run no checks when Actions opens them

- **What:** `promote-to-main.yml:28-31` self-documents that a PR opened with the built-in `GITHUB_TOKEN` does not trigger `pull_request` workflows — so `leak-guard.yml` does not auto-run on the promote PR.
- **Why:** Observed live twice on 2026-08-13 (PRs #65 and #68 both showed "no checks reported" until manually closed and reopened under a user token). The release path is exactly where content sanitization must not be skippable by accident.
- **Disposition:** ADOPT. Either open the PR with a user token, or have `/promote` assert that checks actually reported before handing off to the human merge.
- **Cost:** Small. The `/promote` assertion is the lower-risk half and can ship alone. **Risk flags:** A user token in Actions widens the credential surface; the `/promote`-side assertion avoids that entirely and is the recommended first move.

### 1.4 No branch-topology gate into `main`

- **What:** Four workflows exist; none restricts which head branches may open a PR into `main`. `leak-guard.yml` gates PR **content**; `promote-to-main.yml` is `workflow_dispatch`-only.
- **Why:** A hand-made feature-branch PR into `main` bypasses the entire sanitization build. This defends LogicLoom's own single-parent invariant, and is the top item (their B1) from the Cosmos handoff.
- **Disposition:** ADOPT, with a design decision attached. **Cost:** Small workflow, non-trivial decision. **Risk flags:** **Overbearing risk.** A customer's `main` topology is not the maintainer's. The gate must be either a strip-manifest dev-only entry or explicitly configurable. Shipping the maintainer's release topology as an unremovable gate in a customer clone directly violates the governing constraint.

### 1.5 Test-suite defects found during the release

- **What:** (a) `list_git_checkpoints` in `common.sh` writes pretty-printed multi-line JSON but reads it back line-by-line through `jq` — which cannot work. The test that should catch this uses `local x=$(cmd)` and then checks `$?`; `local` always resets `$?` to 0, so the assertion can never fail. (b) `create_git_checkpoint` writes into `.logic-loom/logs/git-checkpoints` during tests with no cleanup, making the suite stateful.
- **Why:** A test that cannot fail is a false green, and it is currently counted in the suite's pass total. Stateful writes mean run order can change results.
- **Disposition:** ADOPT both. Fix the `local`/`$?` idiom, fix the JSON read, isolate or clean the checkpoint dir. **Cost:** Small. **Risk flags:** None protected. Expect the assertion count to move once the test can actually fail — do not treat that as a regression.

### 1.6 Product-name leak in a shipped test comment

- **What:** `tests/contract/test_product_workspace_boundary.sh:7` reads "cosmos lost ~801 spec files to this" — naming an unrelated private project in a file that ships to every customer.
- **Why:** Cosmetic, but it is a private-project name in public distribution.
- **Disposition:** ADOPT. One-line reword to a generic description of the failure mode. **Cost:** Trivial. **Risk flags:** None.

## 2. Prevention tests — close the classes, not the instances

Both exist because the v6.4.0 release leaked something the tooling had no way to know about. Fixing the instance without the class guarantees a repeat.

### 2.1 Generated-artifact ship/strip declaration test

- **What:** A contract test asserting every git-tracked **generated** artifact is either listed in the strip manifest or explicitly declared shippable.
- **Why:** The v6.4.0 promote leaked the owner's domain via `.logic-loom/graph/graph-bridge.jsonl`, a generated index added *after* the previous release. The strip tooling had no mechanism to learn about a new file class; it only knew what it had been told.
- **Disposition:** ADOPT. **Cost:** Medium — requires a reliable "is generated" signal (producer-script manifest or an explicit allowlist file); a heuristic will produce false positives. **Risk flags:** Not protected. Must fail loudly on *unknown* files, not silently default to shippable.

### 2.2 Scrub rules must match something

- **What:** A test asserting each scrub rule actually matches at least one thing, so a no-op rule fails loudly.
- **Why:** 19 dated-stamp rules in `history-scrub-rules.json` were pinned to literal dates, silently stopped matching once those dates rotated, and a missed op is only a *warning*. They rotted unnoticed for roughly seven weeks.
- **Disposition:** ADOPT. Consider also promoting "rule matched nothing" from warning to error in the scrub tool itself. **Cost:** Small. **Risk flags:** Some rules are legitimately conditional; the test needs an opt-out marker or it becomes the noisy check people learn to ignore — the §1.2 failure mode.

## 4. GitHub issue #55 (gh telemetry) — REFRAMED, not closed

- **What the issue proposes:** write `telemetry: disabled` into `~/.config/gh/config.yml` **and** append `export GH_TELEMETRY=0` to the user's `~/.zshrc` / `~/.bashrc` during setup.
- **Why this is refused as written:** it conflicts with the harness↔user boundary documented in `CLAUDE.md` and `START_HERE.md`. LogicLoom writes nothing outside the repo; this reaches past `~/.claude/` into shell configuration, machine-wide, affecting every non-LogicLoom shell the user opens. That is the definition of overbearing.
- **The irony worth stating:** the issue justifies itself with Principle VI — approval before anything leaves the machine — but silently editing a shell rc during bootstrap is itself precisely the unapproved action Principle VI exists to prevent.
- **Also:** the issue predates the rename and references paths that no longer exist (`.specify/scripts/`, `SDD_SKIP_PRIVACY_HARDENING`, `sdd-agentic-framework`). It cannot be implemented as written regardless of the boundary question.
- **Proposed replacement:** **detect** that `gh` telemetry is enabled, inform the user once with the exact one-line opt-out command, and let them run it. Optionally `/initialize-project` may **offer** to run it with explicit confirmation. Same outcome for anyone who cares; zero writes outside the repo.
- **Disposition:** Keep the issue **open**, retitled and rescoped — do not close. The underlying concern is legitimate; only the mechanism is wrong.
- **Cost:** Small. **Risk flags:** None, provided detection is read-only and remediation stays user-invoked.

## 7. Governance hook redesign — remaining stages

Staged plan produced by an advisor consult on 2026-08-14. Stages 1–2 shipped (see "Completed 2026-08-14"); 3–4 are open and should land together.

- **Stage 1 — tokenizer fix. DONE (`66e4dbf`).**
- **Stage 2 — close the gating inversion. DONE (`38b0144`).**

### 7.3 Subagent read-only git allowlist — NOT DONE

- **What:** Let subagents run known-safe read-only git commands instead of being denied categorically.
- **Design constraint (from the advisor, non-negotiable):** build it as **allowlist known-safe reads, deny everything else** — never "classify mutations and allow the remainder." Unknown subcommand, unknown flag, any command separator or substitution → **deny**. The inline fallback stays categorical.
- **Why the constraint:** an allowlist fails **false-positive** — loud, self-announcing, fixed in a day. A denylist fails **false-negative** — a silent subagent mutation, the exact outcome Principle VI exists to prevent.
- **Disposition:** ADOPT, with the allowlist shape fixed. Do not accept a denylist implementation. **Cost:** Medium. **Risk flags:** ***(protected)*** — edits the subagent git guard.

### 7.4 Doc reconciliation for the changed guarantee — NOT DONE

- **What:** With §7.3, the guarantee changes from "subagents never touch git" to "subagents never **mutate** git." That is a claim change, not a wording change.
- **Where:** `.docs/architecture/governance-threat-model.md`, `CLAUDE.md`, and `AGENTS.md`, updated in tandem.
- **Disposition:** ADOPT, sequenced with §7.3 in the same change. Shipping §7.3 alone leaves the shipped threat model overstating the floor.
- **Cost:** Small. **Risk flags:** ***(protected)***.

### Rejected on advice — do not re-propose

- **(a) Four-tier risk taxonomy.** The four tiers collapse to two runtime decisions (allow / ask) — the binary that already exists — while adding a maintenance surface that must track every `git` and `gh` release. Cost with no decision-making gain.
- **(b) Session-scoped user-intent token read by PreToolUse.** Any intent channel writable during the session is forgeable by the very agent it constrains. Also: keyword crudeness ("don't push yet" contains "push"), staleness across a long session, and inevitable scope creep.

**Supporting finding — user intent is not knowable at PreToolUse.** The hook payload carries `tool_name`, `tool_input`, `agent_id`, `agent_type`, and `session_id`. There is **no prompt field**. `transcript_path` and `permission_mode` are referenced **nowhere** in this repo. Any design premised on the hook knowing what the user asked for is premised on data the hook does not receive.

## 8. New investigation findings (2026-08-14)

### 8.1 Plugin externalization is not a refactor *(constitutional)*

- **The easy half:** `kelleysd-apps/sdd-plugins-marketplace` exists, is **private, NOT archived**, last pushed 2026-02-06, and contains the pre-rename `sdd-*` generation — including plugins deleted months ago (`sdd-debug`, the seven `sdd-domain-*`). Nothing in LogicLoom references it except one already-banner-marked historical doc. **Archiving it is zero-risk** and can proceed independently.
- **The hard half:** "all plugins from third-party sources" is a different proposition. `loom-governance` **is** the hook floor — a user-disablable marketplace plugin is not a floor (the repo's own `features/modular-harness/exploration/unified-architecture.md` reaches this conclusion verbatim). `loom-git`'s entire value is being the *approved path* through Principle VI. `loom-orchestrator` depends on the freeze DAG, loom-memory, and the `features/<name>/` layout. Roughly **1.5 of 8** plugins could leave cleanly: `sdd-specification`, and parts of `loom-creation` after decoupling.
- **Breakage surface:** all **19** bridged commands are pointers into `plugins/` with **zero static fallbacks**. Removal deletes `/swarm`, `/research`, `/cross-check`, `/git-push`, `/promote`, and `/update-framework`.
- **Constitutional blocker:** Principle XVI requires every plugin to declare `loom-governance` as a dependency — which a harness-agnostic third-party plugin cannot do. Externalization therefore requires a **constitutional amendment**, not just tooling.
- **Direct contradiction:** VISION.md Open Thread #8 and the modular-harness design both propose **adding** `marketplace.json` so this repo becomes its own marketplace — the opposite direction. One must be withdrawn before either is designed.
- **Disposition:** SPLIT. Archive the stale marketplace repo now; hold externalization pending a direction call. **Cost:** Archive, trivial. Externalization, large and constitutional. **Risk flags:** ***(constitutional)***.

### 8.2 Shipped branching and deployment policies describe a repo that does not exist

- **What:** `.docs/policies/branching-strategy-policy.md` prescribes GitFlow (`main` + `develop` + `release/*`). **`dev-main` appears nowhere in `.docs/policies/`.** `.docs/policies/deployment-policy.md` asserts deployment is "automatic on push to `staging`" — there is no `staging` branch. Both files ship to customers.
- **Why:** Same defect class as the rotted scrub rules (§2.2): policy describing machinery that is not there. A customer following the shipped branching policy will build a topology the tooling does not support.
- **Disposition:** ADOPT. Rewrite both to describe the actual `dev-main` → `main` model, or mark them explicitly aspirational. **Cost:** Small. **Risk flags:** None protected. Customer-visible, so correctness matters more than speed.

### 8.3 Multi-environment promotion — where the line falls

- **What:** 100% of today's promote machinery is maintainer-only and stripped, so customers inherit **nothing** to build on. `deployment-policy.md` already contains a full dev/staging/prod model in prose — per-environment characteristics, triggers, production gates, approval matrix — that **nothing reads**. `promote-to-main.yml` already uses `environment: release` as a human-approval gate; it is the **only GitHub Environment in the repo** and the natural thing to generalize.
- **Recommended harness scope:** an environment **declaration schema** (`.logic-loom/config/environments.conf`: name, branch, gates, approval required, promotion predecessor), the generalized gate structure, Principle VI approval at each boundary, and the §8.2 docs reconciliation.
- **Explicitly NOT the harness's job:** which cloud, which CI, deploy commands, secrets store, migration runner, rollback mechanics. Those belong to the product behind a declared `deploy:` seam.
- **Name collision:** `/promote` is stripped by **exact path** in the manifest, so a customer-facing `/promote <env>` needs either a different name or a manifest restructure. Unresolved.
- **Counter-argument to weigh first:** Principle V (Progressive Enhancement) argues against shipping a full three-environment pipeline before a single one is proven in use.
- **Disposition:** DECIDE before building. The schema-only scope is the defensible minimum; the rest is speculative. **Cost:** Medium if scoped to the schema + gate structure; large if it grows deploy execution. **Risk flags:** **Overbearing risk** — a shipped environment model is an opinion about the customer's infrastructure. Keep it declarative and overridable.
