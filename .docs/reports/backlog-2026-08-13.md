## Governing constraint

Every disposition below was decided against the maintainer's stated goal, verbatim:

> "give LogicLoom users a clear usable harness from the install but not overbearing on their own preferences they may want to implement."

That cuts both ways. It **rejects** anything that reaches outside the repo, hardcodes the maintainer's own topology into a customer's tree, or ships an opinion a fork cannot override (§4, §3.1's caveat, §1.4's risk). It also **rejects** shipping a check that lies about what it verified, because a broken default is not a neutral one (§1.1, §1.2). "Not overbearing" means configurable and honest — not absent.

The constraint held through implementation: §1.4's topology gate ships dev-only, §3.1's protected paths are additive-only over an un-removable floor, §4 writes nothing outside the repo, and §8.3 declares environments without deploying to any of them.

## 7. Governance hook redesign — all four stages shipped

- **7.1 Tokenizer fix — DONE (`66e4dbf`).** Command-position anchoring for invocation detection, subcommand anchoring for mutation detection, same fix in `protect-governance-files.sh`. Removed false denials (`grep --exclude-dir=.git`, `sed -i.bak`, `ls foo/.git`, even `echo "check git status later"`) and closed two false ALLOWs in passing — bare `git branch <new>` was ungated, and a line-leading `rm`/`mv` against a protected path bypassed protection entirely. Verdict table 54/62 → 62/62; protected-path 44/56 → 56/56.
- **7.2 Gating inversion — DONE (`38b0144`).** `gh pr create|merge` and `gh workflow run` had matched *no* hook or policy at all. Now gated across pr/workflow/run/release/repo/issue/alias/secret/ssh-key/auth plus `git worktree` mutations. Three laundering vectors closed: `gh api -X PUT …/merge`, `gh api -f/-F` (defaults to POST), and `gh alias set`. Subagents are denied `gh` wholesale including reads — deliberately categorical. Force-push moved from hard block to `require_approval`, satisfying "the hook should not stop the ask." **Test-integrity note:** the assertion for the old hard block was flagged and replaced with a group proving force-push is still gated — not silently weakened.
- **7.3 Subagent read-only git allowlist *(protected)* — DONE (`f2bdf06`).** Built as **allowlist known-safe reads, deny everything else**, as the design constraint required. Unknown subcommand, unknown flag, any command separator or substitution → deny. Code-executing globals (`-c`, `--git-dir`, `--work-tree`, `--exec-path`) denied. The inline fallback stays categorical.
- **7.4 Doc reconciliation *(protected)* — DONE (`f2bdf06`, same commit).** The guarantee changed from "subagents never touch git" to "subagents never **mutate** git" — a claim change, not a wording change. `governance-threat-model.md`, `CLAUDE.md`, `AGENTS.md` updated in tandem so the shipped threat model does not overstate the floor.
- **Same commit also registered four orphaned test suites** that existed on disk but were never invoked by the runner. That is the largest single reason the assertion count jumped.

### Rejected on advice — do not re-propose

**(a) Four-tier risk taxonomy** — collapses to the allow/ask binary that already exists, while adding a surface that must track every `git` and `gh` release. **(b) Session-scoped user-intent token read by PreToolUse** — any intent channel writable during the session is forgeable by the agent it constrains.

**Supporting finding — user intent is not knowable at PreToolUse.** The hook payload carries `tool_name`, `tool_input`, `agent_id`, `agent_type`, `session_id`. There is **no prompt field**. `transcript_path` and `permission_mode` appear nowhere in this repo. Any design premised on the hook knowing what the user asked for is premised on data the hook does not receive.

> **Correction 2026-08-24 (LOOM-0031).** The last two sentences of that supporting finding overstate an absence. `transcript_path` and `permission_mode` are absent from *this repo's hooks*, but they are **present in the PreToolUse payload** — the runtime's base hook input is `{ session_id, transcript_path, cwd, prompt_id, permission_mode, agent_id, agent_type, effort }` (verified against the Claude Code 2.1.200 bundle). "No prompt field" remains correct, and the decisions above are unaffected: a transcript path is a file the hook would have to read and interpret at tool-call latency, and `permission_mode` says what mode is active, not what the user asked for. But the rejection of (b) should rest on the forgeability argument, not on the claim that the data is not delivered.
