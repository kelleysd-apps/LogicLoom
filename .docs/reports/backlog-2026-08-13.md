# LogicLoom Consolidated Backlog — 2026-08-13

**Status:** PROPOSED — nothing in this document is applied. Every item requires explicit approval before implementation, per the standing principle: **propose before editing existing framework systems** (and Principle VI: no autonomous mutation of the governance/orchestration surface). Items that touch a protected governance file or ratified constitutional text are flagged *(protected)* / *(constitutional)*; those carry a second main-agent approval gate at apply-time regardless of this document's acceptance.

**Author:** LogicLoom lead architect
**Scope:** LogicLoom v6.4.1 / constitution v3.2.0
**Sources:** (1) review of a downstream contribution handoff from the Cosmos project, (2) defects and follow-ups surfaced during the v6.4.0 / v6.4.1 release work on 2026-08-13, (3) GitHub issue #55.

---

## Governing constraint

Every disposition below was decided against the maintainer's stated goal, verbatim:

> "give LogicLoom users a clear usable harness from the install but not overbearing on their own preferences they may want to implement."

That cuts both ways. It **rejects** anything that reaches outside the repo, hardcodes the maintainer's own topology into a customer's tree, or ships an opinion a fork cannot override (§4, §3.1's caveat, §1.4's risk). It also **rejects** shipping a check that lies about what it verified, because a broken default is not a neutral one (§1.1, §1.2). "Not overbearing" means configurable and honest — not absent.

## 1. Verified defects (BUGS, not enhancements)

These are not proposals to improve the harness; they are things the harness currently gets wrong.

### 1.1 `constitutional-check.sh` overstates its own result

- **What:** `.logic-loom/scripts/bash/constitutional-check.sh` has exactly **one** `record_fail` call site (line 194, Principle VI) against **17** `record_warn` calls. Principle X is labelled `(CRITICAL)` at line 284, but its only outcome is `record_warn` at line 310. Line 531 prints `"All critical principles (VI, X) are met."` inside `if [ $FAIL_COUNT -eq 0 ]` — a condition Principle X can never influence.
- **Why:** The script asserts it verified X and structurally cannot. A compliance check that reports a stronger result than it computed is worse than one that reports nothing.
- **Disposition:** ADOPT. Either make X able to fail, or delete "X" from the success string. Recommend the second as the minimum honest fix, with the first as the follow-up — making X hard-fail changes exit codes for every existing consumer and should be its own decision.
- **Cost:** Minimum fix, one line. Full fix (X can fail) small, but touches exit-code contract.
- **Risk flags:** Not a protected file. Making X fail could break CI for downstream clones — gate behind a flag or ship as a minor-version behavior change.
- **Note:** Independently disclosed by Cosmos in their handoff §8. It is inherited from the shared ancestor and is present in both trees.

### 1.2 Stale `.claude/agents/` warning contradicts a ratified decision

- **What:** The same script warns (line 445) that `.claude/agents/` is legacy and agents belong in `plugins/*/agents/`.
- **Why:** Keeping `deep-reasoner` and `fast-worker` as **project** agents there was a deliberate v6.3.1 decision — plugin agents lose `hooks`, `mcpServers`, and `permissionMode`. A warning that fires on a correct configuration trains maintainers to ignore the check wholesale, which erodes §1.1's fix too.
- **Disposition:** ADOPT. Narrow the warning to unexpected entries, or drop it.
- **Cost:** Trivial.
- **Risk flags:** None. Not protected.

### 1.3 Promote PRs run no checks when Actions opens them

- **What:** `promote-to-main.yml:28-31` self-documents that a PR opened with the built-in `GITHUB_TOKEN` does not trigger `pull_request` workflows — so `leak-guard.yml` does not auto-run on the promote PR.
- **Why:** Observed live twice on 2026-08-13 (PRs #65 and #68 both showed "no checks reported" until manually closed and reopened under a user token). The release path is exactly where content sanitization must not be skippable by accident.
- **Disposition:** ADOPT. Either open the PR with a user token, or have `/promote` assert that checks actually reported before handing off to the human merge.
- **Cost:** Small. The `/promote` assertion is the lower-risk half and can ship alone.
- **Risk flags:** A user token in Actions widens the credential surface; the `/promote`-side assertion avoids that entirely and is the recommended first move.

### 1.4 No branch-topology gate into `main`

- **What:** Four workflows exist; none restricts which head branches may open a PR into `main`. `leak-guard.yml` gates PR **content**; `promote-to-main.yml` is `workflow_dispatch`-only.
- **Why:** A hand-made feature-branch PR into `main` bypasses the entire sanitization build. This defends LogicLoom's own single-parent invariant, and is the top item (their B1) from the Cosmos handoff.
- **Disposition:** ADOPT, with a design decision attached.
- **Cost:** Small workflow, non-trivial decision.
- **Risk flags:** **Overbearing risk.** A customer's `main` topology is not the maintainer's. The gate must be either a strip-manifest dev-only entry or explicitly configurable. Shipping the maintainer's release topology as an unremovable gate in a customer clone directly violates the governing constraint.

### 1.5 Test-suite defects found during the release

- **What:** (a) `list_git_checkpoints` in `common.sh` writes pretty-printed multi-line JSON but reads it back line-by-line through `jq` — which cannot work. The test that should catch this uses `local x=$(cmd)` and then checks `$?`; `local` always resets `$?` to 0, so the assertion can never fail. (b) `create_git_checkpoint` writes into `.logic-loom/logs/git-checkpoints` during tests with no cleanup, making the suite stateful.
- **Why:** A test that cannot fail is a false green, and it is currently counted in the suite's pass total. The stateful writes mean run order can change results.
- **Disposition:** ADOPT both. Fix the `local`/`$?` idiom, fix the JSON read, and isolate or clean the checkpoint dir.
- **Cost:** Small.
- **Risk flags:** None protected. Expect the assertion count to move once the test can actually fail — do not treat that as a regression.

### 1.6 Product-name leak in a shipped test comment

- **What:** `tests/contract/test_product_workspace_boundary.sh:7` reads "cosmos lost ~801 spec files to this" — naming an unrelated private project in a file that ships to every customer.
- **Why:** Cosmetic, but it is a private-project name in public distribution.
- **Disposition:** ADOPT. One-line reword to a generic description of the failure mode.
- **Cost:** Trivial.
- **Risk flags:** None.

## 2. Prevention tests — close the classes, not the instances

Both of these exist because the v6.4.0 release leaked something the tooling had no way to know about. Fixing the instance without the class guarantees a repeat.

### 2.1 Generated-artifact ship/strip declaration test

- **What:** A contract test asserting every git-tracked **generated** artifact is either listed in the strip manifest or explicitly declared shippable.
- **Why:** The v6.4.0 promote leaked the owner's domain via `.logic-loom/graph/graph-bridge.jsonl`, a generated index added *after* the previous release. The strip tooling had no mechanism to learn about a new file class; it only knew what it had been told.
- **Disposition:** ADOPT.
- **Cost:** Medium — requires a reliable "is generated" signal (producer-script manifest or an explicit allowlist file); a heuristic will produce false positives.
- **Risk flags:** Not protected. Must fail loudly on *unknown* files, not silently default to shippable.

### 2.2 Scrub rules must match something

- **What:** A test asserting each scrub rule actually matches at least one thing, so a no-op rule fails loudly.
- **Why:** 19 dated-stamp rules in `history-scrub-rules.json` were pinned to literal dates, silently stopped matching once those dates rotated, and a missed op is only a *warning*. They rotted unnoticed for roughly seven weeks.
- **Disposition:** ADOPT. Consider also promoting "rule matched nothing" from warning to error in the scrub tool itself.
- **Cost:** Small.
- **Risk flags:** Some rules are legitimately conditional; the test needs an opt-out marker or it will become the noisy check people learn to ignore — the §1.2 failure mode.

## 3. Adopt from the Cosmos handoff

**Review basis.** The handoff was reviewed against `dev-main`, not against a stripped tree. Two of its findings are artifacts of reading a sanitized copy and are **struck**:

- Its claim that `promote-to-main.yml` references missing scripts — **false on dev-main**. Those scripts are deliberate strip-manifest entries; they are absent from the template line by design.
- Its claim that `VISION.md` is an unfilled stub — **false on dev-main**. VISION.md is 330 lines, v2.0, with populated numbered Open Threads.

### 3.1 Make `loom_path_is_protected()` config-driven

- **What:** `.logic-loom/lib/governance-verdicts.sh:77-88` hardcodes the protected-path set to `.logic-loom/…` and `plugins/loom-governance/…`. A fork using different directory names gets a **silently broken** governance-file guard — no error, just no protection.
- **Why:** This is the real answer to the handoff's §10 Q1, and it is **not** an item they proposed. `.logic-loom/config/governance.conf` already exists and is already parsed with documented `env > file > built-in` precedence, so a `protected_paths` key follows an established pattern rather than inventing a surface.
- **Disposition:** ADOPT, subject to the caveat below.
- **Cost:** Small–medium.
- **Risk flags:** ***(protected)*** — edits the governance verdict library. **CRITICAL CAVEAT:** the protected-path list must itself be protected, or a fork (or the model) can edit its own guard list and unlock everything. The config key must be self-including, with the built-in defaults as an un-removable floor rather than a replaceable default. Get this wrong and the item is a privilege-escalation hole, not a portability win.

### 3.2 Constitution addendum layering *(constitutional)*

- **What:** Their D1 — a documented extension point letting a fork layer project-specific mandates without editing ratified principle bodies in place. Fold their D2 ("named mandates") into this rather than opening a second extension surface.
- **Why:** Directly serves "not overbearing on their own preferences." Today a fork's only route is to edit ratified text, which destroys the upstream merge story.
- **Disposition:** ADOPT, sequenced last.
- **Cost:** Medium. Requires a constitution version bump and tandem `CLAUDE.md` / `AGENTS.md` sync.
- **Risk flags:** ***(protected)*** + ***(constitutional)*** — touches `constitution.md`, a protected governance file carrying ratified text. Immutable principles I–III must remain un-overridable by an addendum, and that must be lint-enforced, not merely documented. Overlaps VISION.md Thread #7 (amendments split) — reconcile before designing, or two extension mechanisms will land.

### 3.3 Fail-closed grounding rule for fast-moving external APIs

- **What:** Their D4 — a short rule requiring verification rather than recall for fast-moving external interfaces.
- **Why:** Nothing in the tree carries such a rule, yet `models.conf` pins specific cross-provider model names that go stale. Placed in the advisory section it strengthens the advisory-only boundary rather than crossing it.
- **Disposition:** ADOPT. Keep it to a short rule; do not build a verification mechanism.
- **Cost:** Small.
- **Risk flags:** None protected, if it stays a documented rule. It becomes an overreach the moment it grows a runtime checker.

### 3.4 Optional `eval` metadata block

- **What:** Their D6 — an optional metadata block in `.claude-plugin/plugin.json` or skill frontmatter, validated by the manifest CI step that already exists.
- **Why:** Additive, opt-in, and it reuses validation already present.
- **Disposition:** ADOPT the metadata block only.
- **Cost:** Small.
- **Risk flags:** **Scope creep is the risk.** Keep the judge and the runner explicitly out of scope; the moment LogicLoom ships an eval executor it has an engine, which contradicts the standing "ride native, don't reimplement" position.

### 3.5 Shell-idiom style guide

- **What:** Their B3 / B4 / B6 / B7 / B10, merged into one policy doc under `.docs/policies/`: merge-abort before restore; scoped `--force-with-lease`; isolated-worktree mutation; `set -e`-safe `rc=0; cmd || rc=$?`; baseline-run-id with bounded waits.
- **Why:** Incident-derived and generic. These are the idioms whose absence produced real failures in both trees.
- **Disposition:** ADOPT as documentation.
- **Cost:** Small.
- **Risk flags:** None. Explicitly a guide, not a linter — a linter here would be overbearing on contributor style.

### 3.6 Publish the plugin manifest schema as a doc

- **What:** Their A1b. The schema effectively exists and CI already validates `name` / `version` / `dependencies`; what is missing is the written spec.
- **Why:** A fork cannot conform to an unwritten contract.
- **Disposition:** ADOPT. Write down what CI already enforces; do not extend it in the same change.
- **Cost:** Small.
- **Risk flags:** None. **Correction to their framing:** the absence of a plugin **registry index** is genuinely undocumented. `plugins/CONTRIBUTING.md:64-75` documents dropping a *marketplace MCP server*, which is a different thing. (VISION.md Thread #8 proposes `marketplace.json` as the answer — sequence that thread, not a second mechanism here.)

## 4. GitHub issue #55 (gh telemetry) — REFRAMED, not closed

- **What the issue proposes:** write `telemetry: disabled` into `~/.config/gh/config.yml` **and** append `export GH_TELEMETRY=0` to the user's `~/.zshrc` / `~/.bashrc` during setup.
- **Why this is refused as written:** it conflicts with the harness↔user boundary documented in `CLAUDE.md` and `START_HERE.md`. LogicLoom writes nothing outside the repo; this reaches past `~/.claude/` into shell configuration, machine-wide, affecting every non-LogicLoom shell the user opens. That is the definition of overbearing.
- **The irony worth stating:** the issue justifies itself with Principle VI — approval before anything leaves the machine — but silently editing a shell rc during bootstrap is itself precisely the kind of unapproved action Principle VI exists to prevent.
- **Also:** the issue predates the rename and references paths that no longer exist (`.specify/scripts/`, `SDD_SKIP_PRIVACY_HARDENING`, `sdd-agentic-framework`). It cannot be implemented as written regardless of the boundary question.
- **Proposed replacement:** **detect** that `gh` telemetry is enabled, inform the user once with the exact one-line opt-out command, and let them run it. Optionally, `/initialize-project` may **offer** to run it with explicit confirmation. Same outcome for anyone who cares; zero writes outside the repo.
- **Disposition:** Keep the issue **open**, retitled and rescoped — do not close. The underlying concern is legitimate; only the mechanism is wrong.
- **Cost:** Small.
- **Risk flags:** None, provided detection is read-only and the remediation stays user-invoked.
